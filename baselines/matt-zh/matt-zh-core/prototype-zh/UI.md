# UI 原型

在**单一路由**上生成**几个差异显著的 UI 方案**，通过屏幕底部浮动栏切换。用户在浏览器里比较、选择一个方案（或组合各方案的部分），其余从主分支移除。

若问题是逻辑/状态，而不是外观，用 [LOGIC.md](LOGIC.md)。

## 适用情形

- “页面应该长什么样？”
- “敲定前想看看仪表盘的几种选择。”
- “设置页换种布局试试。”
- 任何用户只能在脑中比较几个模糊 mockup、需要看到实物的情形。

## 两种形态：优先选 A

UI 原型紧贴应用的其他部分时更易判断：真实的页头、侧栏、数据与信息密度。独立临时路由缺少上下文，孤立地看每个方案都不错。只要存在适合承载方案的现有页面，默认选 A；只有确实没有邻近位置时才选 B。

### A：调整现有页面（优先）

路由已经存在。通过 `?variant=` URL 参数在**同一路由**渲染不同方案。保留原有数据获取、参数及认证，只替换展示层。这是默认方案，没有特定理由就不要改选。

即使原型还没有独立页面，只要自然属于已有页面的一部分（例如仪表盘新区块、设置页新卡片、现有流程的新步骤），也属于形态 A：把方案挂在宿主页面内部。

### B：新页面（最后手段）

仅当所探索的内容确实没有可嵌入的已有页面（全新顶层界面、无法合理嵌入的流程）时使用。

依照项目既有路由规范创建**临时路由**，不要发明新的顶层结构。名称明显标识为原型（如路径或文件名含 `prototype`），同样采用 `?variant=`。

选择 B 前再确认一次：真的没有现有页面可容纳它吗？空白路由会隐藏真实内容页才能暴露的设计问题。

两种形态使用相同的浮动底栏。

## 流程

### 1. 说明问题并确定方案数量

默认 **3 个方案**，最多 5 个；更多方案往往只增添噪声，差异不再显著。

在原型所在位置或文件顶部注释中，用一行记下计划：

> “在已有 `/settings` 路由上，通过 `?variant=` 切换设置页的三个方案。”

不论用户是否在线，这都便于之后检查。

### 2. 生成真正不同的方案

每个方案都遵守：

- 页面目标和可获取的数据。
- 项目的组件库/样式体系（TailwindCSS、shadcn、MUI、普通 CSS 等）。
- 清晰的导出组件名，如 `VariantA`、`VariantB`、`VariantC`。

方案必须在**结构上有区别**：布局、信息层级、主要交互方式不同，不能只是颜色不同。三个稍改的卡片网格不算 UI 原型，只是装饰。若两个草稿太像，明确要求“不使用卡片网格”，重做其一。

### 3. 接线

在路由上创建单个切换组件：

```tsx
// 伪代码；按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

形态 A：原有数据获取保留在切换器上方，只替换渲染的子树。形态 B：`/prototype/<name>` 下临时路由挂载同样的切换器。

### 4. 制作浮动切换器

屏幕底部居中的小型固定栏，包含三部分：

- **左箭头**：循环切换到上一个方案。
- **方案标签**：显示当前方案代号，若有名称也显示，如 `B（侧栏布局）`。
- **右箭头**：循环切换到下一个方案。

行为：

- 点击箭头更新 URL 参数（用框架路由，如 Next 的 `router.replace`、React Router 的 `navigate`），使方案可分享、刷新后仍稳定。
- 键盘方向键 `←` 和 `→` 同样可切换。焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 时不要拦截方向键。
- 视觉上与页面本身区分（如高对比药丸按钮、轻阴影），让人知道它不属于待评估的设计。
- 生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查兜底，以免误合并将切换器交付用户。

将切换器做成单个共享组件，两种形态都能复用；放在项目共享 UI 的既有位置。

### 5. 交给用户

给出 URL 和 `?variant=` 的取值。用户随时可切换查看；真正有价值的反馈可能是“我想要 B 的页头加 C 的侧栏”，这才是他们真正想要的设计。

### 6. 保存结论并清理

某方案胜出后，记录选择与原因，按 [SKILL.md](SKILL.md) 保存原型。将胜出方案融入正式代码，其余内容移到临时分支，不留在 main：

- **形态 A**：将胜出方案融入现有页面，从 main 删除落选方案和切换器。
- **形态 B**：将胜出方案升级为正式路由，从 main 删除临时路由和切换器。

完整方案集是第一手资料，应留在临时分支，而不是删除；原型组件和切换器若留在主分支会腐烂并误导后续读者。

## 反模式

- **只改颜色或文案的方案。**那是微调，不是原型；真正的方案应在结构上有分歧。
- **方案之间共享过多代码。**共享 `<Header>` 没问题，共享 `<Layout>` 会破坏探索。每个方案都应能替换整个布局。
- **连接真实数据变更。**只读原型足够；若需修改数据，用桩代替。要回答的是“长什么样”，不是“后端是否正常”。
- **直接将原型投产。**原型代码按无测试、最少错误处理的限制编写；融入正式代码时要按生产标准重写。
