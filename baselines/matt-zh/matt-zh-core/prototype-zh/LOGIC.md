# 逻辑原型

一个独立的 HTML 文件（**可分享演示**），让任何人点击按钮来推动状态模型。适用于**业务逻辑、状态转换或数据形状**问题：在纸面上似乎合理，代入真实案例后才察觉不对。

只有一个文件，无需安装，因此可以交给非开发者（设计师、产品经理、领域专家）亲自体验模型。界面应使用他们的语言，而非代码术语。

## 适用情形

- “不确定状态机能否处理先发生 X 再发生 Y 的边界情况。”
- “这个数据模型真的能表达……这样的情况吗？”
- “编写 API 前，想先体验它该是什么形态。”
- 任何希望**点击按钮并观察状态变化**的情形。

若问题是“应该长什么样”，则用 [UI.md](UI.md)，不要走此分支。

## 流程

### 1. 明确问题

写代码前，用一段话写明原型要验证的状态模型和问题，放在演示页顶部、用户可见的位置（不能只有注释）。答错问题的原型纯属浪费；明确问题还能让用户当下或稍后异步核对。

### 2. 将逻辑隔离为可移植模块

把真正回答问题的逻辑写在一个 `<script>` 块里，设计为小型纯模块，可在后续移入正式代码。页面外围可丢弃，逻辑模块不是。

根据问题选择结构：

- **纯 reducer**：`(state, action) => state`。适用于动作是离散事件、状态是单一值。
- **状态机**：显式列出状态与转换。适用于“眼下哪些操作合法”也是问题的一部分。
- **基于普通数据类型的一组纯函数**：适用于没有隐含的当前状态、只有数据转换的情形。
- **方法界面明确的类或模块**：只在逻辑确实拥有持续的内部状态时使用。

选最贴合所问问题的结构，不是最容易接入页面的结构。逻辑必须纯粹：不读 DOM、不引用 `document`，按钮处理器不能伸入其内部。页面调用它，反方向没有依赖。这样问题回答后，验证过的 reducer、状态机或函数集可独立移入正式模块。

### 3. 构建可分享的 HTML 文件

一个纯 HTML/CSS/JS 文件：没有框架、打包器或服务器；内容都内联，双击可打开，也能作为附件发送。任何人打开文件就能运行。

面向非开发者：按钮和状态标签都用**领域语言**，不要用 reducer 的代码术语。用普通语言说明发生了什么。

页面从上到下保持清晰层次：

1. **标题和一句话说明**：这个演示能探索什么（步骤 1 的问题）。
2. **当前状态**：在易读面板中显示完整相关状态（带标签的字段，而非原始 JSON）。每次点击后重新渲染，让变化可见；必要时指出刚变化了什么。
3. **自由操作按钮**：每种动作一个按钮，始终可用，让任何人按任意顺序探索。点击后派发动作并刷新状态。
4. **引导演示**：每个**场景**一个标签页。各页用简短普通语言说明情境与观察重点，下面是该场景有顺序的**操作按钮**。每一步都是真按钮：点击执行动作并移到下一步。开始演示时重置为已知初始状态，让每次结果一致。

场景覆盖纸面难以推理的情况：正常路径、棘手边界，以及本应非法的操作尝试。

界面美观但克制：清晰排版、充足留白、一种强调色。不要动画或花哨效果，不要让视觉抢走对状态和按钮的注意力。

### 4. 交给用户

发送文件或帮用户打开。用户可立即或稍后走引导场景和自由探索；最有价值的瞬间是他们说“等等，这不应该被允许”或“我以为 X 会不一样”：这就是*想法*中的 bug，也是原型的目的。若需要新动作或新场景，就添加；原型可以演进。

### 5. 保存结论和原型

回答问题后，按 [SKILL.md](SKILL.md) 保存结论与原型。逻辑分支的具体映射：验证过的 reducer、状态机或函数集移入正式模块（吸收决策）；HTML 外壳留在保存原型作为第一手资料的临时分支中。独立文件使之随时可再次运行。

## 反模式

- **不要添加测试。** 需要测试的原型就不再是原型。
- **不要连接真实数据库。** 除非问题专门涉及持久化，否则用内存状态。
- **不要泛化。** 不讨论“以后若支持 X 怎么办”；只回答一个问题。
- **不要混合逻辑与页面。** 若纯模块引用 DOM、`document` 或按钮处理器，就无法移植。页面只是纯模块上的薄外壳。
- **不要使用框架、打包器或服务器。** 接收者要双击单文件；React app 或开发服务器会破坏“可分享”。
- **不要把 HTML 外壳投入生产。** 页面为手动点击设计，值得保留的是其后的逻辑模块。
