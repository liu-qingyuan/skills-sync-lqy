# GLOSSARY.md 格式

## 结构

```md
# {上下文名称}

{用一到两句话说明这个上下文是什么，以及为什么存在。}

## 语言

**订单**：
{用一到两句话定义这个术语。}
_Avoid_：购买、交易

**发票**：
交付后发给客户的付款请求。
_Avoid_：账单、付款通知

**客户**：
下单的人或组织。
_Avoid_：委托人、买家、账户
```

## 规则

- **明确取舍。** 同一概念有多个名称时，选最合适的一个，并将其他名称列在 `_Avoid_` 下。
- **定义要紧凑。** 最多一到两句话。定义它*是什么*，而不是它*做什么*。
- **只记录本项目上下文特有的术语。** 通用编程概念（超时、错误类型、工具函数模式）即使被大量使用，也不属于这里。添加前先判断：这是本上下文独有的领域概念，还是一般编程概念？只收入前者。
- **自然成组时再分组。** 术语自然形成不同主题时使用小标题；全部属于一个连贯领域时平铺即可。

## 单上下文与多上下文仓库

**单上下文（绝大多数仓库）：**根目录有一个 `GLOSSARY.md`。

**多上下文：**根目录的 `GLOSSARY-MAP.md` 列出上下文、位置与关系：

```md
# 术语表地图

## 上下文

- [订单](./src/ordering/GLOSSARY.md)：接收并跟踪客户订单
- [计费](./src/billing/GLOSSARY.md)：开具发票并处理付款
- [履约](./src/fulfillment/GLOSSARY.md)：管理仓库拣货和发货

## 关系

- **订单 → 履约**：订单发出 `OrderPlaced` 事件；履约消费该事件以开始拣货
- **履约 → 计费**：履约发出 `ShipmentDispatched` 事件；计费消费该事件并开具发票
- **订单 ↔ 计费**：共享 `CustomerId` 与 `Money` 类型
```

Skill 根据现有文件推断适用哪种结构：

- 若存在 `GLOSSARY-MAP.md`，阅读它以定位上下文。
- 若只存在根目录的 `GLOSSARY.md`，则为单上下文。
- 若两者都不存在，首个术语确定时再按需创建根目录 `GLOSSARY.md`。

多上下文时先推断当前主题所属的上下文；不明确时再询问。
