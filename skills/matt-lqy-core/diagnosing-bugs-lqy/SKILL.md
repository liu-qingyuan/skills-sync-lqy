# 诊断 Bug

针对实际故障建立反馈循环，不凭阅读代码宣布修复。仅在有明确理由时跳过阶段。

读取项目指定的领域术语表和相关 ADR；新项目默认 `GLOSSARY.md`，旧项目继续使用已配置的同一份术语表。

## 展示边界

**仅在展示副本或回复摘录中隐藏已确认的凭据值**，以 `<REDACTED>` 表示；字段、结构、类型、错误和关联信息保持诊断所需的完整性。普通业务 ID、路径和 URL 不因看起来敏感就被删除。

脱敏不修改 `.env`、原始日志、HAR、业务数据、数据库、fixture 或本地复现输入，不把 `<REDACTED>` 写回原件或发送给真实 API。复现仍使用真实凭据；已有环境变量可用于调试命令，避免将值写进新脚本或回复。不迁移应用配置，不新增安全依赖、认证机制、hook 或检查流程。

如果隐藏会丢失必要的诊断信号，先向用户说明冲突和所需信息，不擅自删字段、改数据或用虚构值替代。需要超出原任务修改权限或配置时，先说明并确认。捕获原件保留，供本地复现；展示摘录不替代证据原件。

## 1. 建立反馈循环

先找到能捕获用户确切症状的一个命令。大致按以下顺序选择足够的方式，不要求全部尝试：

1. 公开接缝上的失败测试：unit、integration 或 E2E。
2. 针对开发服务的 HTTP / curl 请求。
3. 固定输入的 CLI 调用，对比已知正确输出。
4. 浏览器脚本，在 DOM、控制台或网络上验证症状。
5. 本地重放真实 trace、请求或事件。
6. 启动足够小的临时测试环境，调用实际故障路径。
7. 固定随机条件的 property / fuzz loop。
8. 已知好坏版本之间的 `git bisect run`。
9. 相同输入经过旧 / 新版本或配置的差异比较。
10. 必须由人点击时，使用 [人工反馈循环模板](scripts/hitl-loop.template.sh)；只捕获观察结果，登录由用户完成。

让循环尽可能快、确定、信号清晰；非确定性故障先提高复现率，而不是假装一次成功就修好了。

**完成条件**：已实际运行命令，失败来自用户症状而非环境、fixture 或拼写问题；说明命令、信号和结果，展示遵守上述边界。不能建立循环时列出已尝试内容并请求缺失条件，不继续猜测，也不擅自改生产环境。

## 2. 复现与最小化

确认是同一个故障，保存确切症状并检查重复运行表现。

在隔离的复现副本中一次减少一个输入、调用者、配置或步骤，每次重跑；只保留仍能捕获原故障的最小场景。最小化不是删除真实业务数据或覆盖原始证据的授权。副本不足以保留故障就回到原始本地场景。

## 3. 假设

测试前提出 3–5 个按证据排序、可证伪的假设，每个说明预测：“若 X 是原因，改变 Y 会让症状消失 / 加重”。展示给用户；无人值守时可按现有证据排序继续，不能替用户作权限、数据或需求决策。

## 4. 定向观察

每个 probe 对应一个预测，一次改变一个变量。优先 debugger / REPL，其次在区别假设的接缝添加必要日志；不要记录所有内容。

临时日志使用唯一 `[DEBUG-...]` 前缀，完成后只清理本次新增部分。性能问题先建立测量基线并 profile，不用更多日志代替测量。

## 5. 修复与回归测试

存在能覆盖真实调用模式的公开 Seam 时，在修复前写回归测试。单调用者测试无法覆盖跨调用链的故障时，不声称已经锁定回归；记录缺失的 Seam，不顺手扩大架构改造。

1. 将最小复现变成失败测试，确认失败原因。
2. 若已通过临时 mutation 强制 RED，与未修改副本做 diff，证明 mutation 确实落地；这不是要求额外制造失败，也不修改生产数据。
3. 实施满足原合同的最小修复，运行测试确认 GREEN。
4. 重跑原始、未最小化的场景，确认实际故障消失。

## 6. 清理与完成

- 原始症状已验证消失，回归测试通过，或明确记录测试表面不足。
- 移除本次 `[DEBUG-...]` instrumentation；临时复现副本删除或放到明确的调试位置，不删除证据原件。
- 在完成摘要记录有效假设、验证命令和限制。
- 需要更大改动时仅记录 follow-up，由用户选择复盘或架构调查；不自动加载并执行环境整改。

Ralph 单 Ticket 的提交、review、关闭与停止规则仍以 `implement-lqy` 和 tracker 契约为准。
