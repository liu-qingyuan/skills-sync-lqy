# 领域建模

主动挑战术语、用具体场景澄清模型，结论明确时及时写入。只是读取领域词汇属于普通探索，不必运行主动建模。

## 一份权威术语表

优先遵守项目的 `docs/agents/domain.md` 或 AGENTS.md 指定路径。新项目默认根 `GLOSSARY.md`；多领域项目通过 `GLOSSARY-MAP.md` 找到相关领域。

未迁移项目若指定 `CONTEXT.md` / `CONTEXT-MAP.md`，继续读写同一份已配置的文档；未配置但仅有旧 CONTEXT 时也沿用它。不自动更名、不创建第二份术语表，迁移需要明确的用户选择。两个文件都存在且没有权威路径时先询问，不猜测并合并。

术语表与 ADR 只在真正有内容时创建。术语表格式见 [GLOSSARY-FORMAT.md](GLOSSARY-FORMAT.md)，决策格式见 [ADR-FORMAT.md](ADR-FORMAT.md)。

```text
/
├── GLOSSARY.md
└── docs/adr/           # 按需创建
```

术语表只保存领域概念，不承载实现细节、spec 或临时笔记。ADR 保存真正的取舍，不重复术语定义。

## 会话纪律

- 用户用词与已定义术语冲突时立即指出，区分不同概念，提出精确规范名称。
- 用具体边界场景检验规则，确认领域关系而非编造系统应有的行为。
- 提问前先读代码、测试、配置、术语表和 ADR；可用且最新的 GitNexus 只帮助定位，关键事实以源码 / 测试验证。不把可查证的事实反问用户。
- 用户描述当前系统时说明已查到的行为；描述未来目标时指出与现状的差异，交由用户决定是否修改业务规则。
- 术语明确后及时更新同一份权威文档；不因讨论名称顺手改代码或清洗数据。

## ADR

仅当同时满足以下条件时提出 ADR：难以逆转、未来读者会疑惑原因、确有替代方案的权衡。否则不写。既有 ADR 冲突必须说明，不静默覆盖。
