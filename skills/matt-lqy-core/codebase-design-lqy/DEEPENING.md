# 深化

在了解依赖关系的前提下，如何安全地深化一组浅模块。本文沿用 [SKILL.md](SKILL.md) 中的词汇 — **模块**、**接口**、**接缝**、**适配器**。

## 加深前确认 Contract

- 先找出应由一个 Module 拥有的知识、不变量和变化原因，再选择合并范围，不按执行顺序或代码相似程度拼装。
- 明确新 Interface 的前置条件、后置条件、错误、副作用和原子性，核对真实调用方；不擅自加强前置条件或削弱后置条件。确需改变可观察行为时，先确认新 Contract 与迁移范围。
- 将现有测试保护的行为映射到新 Interface，确认失败路径和独有回归有去处，再替换旧实现；不要以“收紧契约”为名新增无关校验或防御层。

## 依赖类别

依赖类别决定如何跨接缝测试，不单独决定是否应该合并 Module。

### 1. 进程内

纯计算、内存状态、没有 I/O。共享知识或变化原因的部分可以直接合并，通过新的 Interface 测试，不需要 Adapter；没有 I/O 不等于应该合并。

### 2. 本地可替代

有本地测试替身的依赖（比如用于 Postgres 的 PGLite、内存文件系统）。替身帮助验证，不证明生产语义等价；按实际 Contract 核对差异。加深后的 Module 可通过内部接缝使用替身，不因测试需要就把端口暴露到外部 Interface。

### 3. 远程但自有（端口与适配器）

你自己拥有、但跨网络边界调用的服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块拥有业务逻辑；传输层作为**适配器**注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/队列适配器。

建议表述：*“在接缝处定义端口，为生产实现 HTTP 适配器，为测试实现内存适配器。这样即使部署跨越网络，逻辑仍然位于一个深模块中。”*

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖作为注入端口接收；测试提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着接缝还只是设想；两个适配器才说明接缝真实存在。** 除非至少有两个适配器有正当理由（通常是生产 + 测试），否则不要引入端口。只有一个适配器的接缝只是多一层间接。
- **区分内部接缝和外部接缝。** 深模块既可以有内部接缝（实现私有、供自身测试使用），也可以在接口处有外部接缝。不要仅仅因为测试会用到内部接缝，就把它们暴露到接口里。

## 测试策略：替换，不叠加

- 先迁移独有行为与失败回归，仅删除已被新测试替代的浅模块实现测试；保留尚未迁移的覆盖及 Adapter 的独立合同测试，不因存在一组新测试就一并删除。
- 在深化后的模块接口上编写新测试。**接口就是测试表面**。
- 测试应通过接口断言可观察结果，而不是内部状态。
- 测试应能经受内部重构——它们描述的是行为，不是实现。如果实现一变测试就必须跟着变，说明测试越过了接口。
