# clean

在明确的文件范围内清除偶然复杂性。用户明确授权行为变化时，以双方确认的新合同为准；否则清理前后的可观察行为、公开合同、必要数据和安全约束必须一致。

## 合同

- 调用方给出文件列表时严格限制在该列表内；否则从请求和真实调用链确定最小范围，并在编辑前说明。
- 不处理范围外问题。如果清理必须改变行为、公开合同、依赖或范围外文件，停止并向用户确认。
- 不新增依赖、配置、Interface、Adapter 或扩展点，除非当前需求证明它们必要。

## 判断依据

- 开始前读取并遵循 `$simple`，按“删除、复用、最小新增”的顺序选择第一个完整解。
- 只有候选改动涉及 Module、Interface、Implementation、Seam、Adapter、Depth 或 Information Leakage 时，才读取并遵循 `$codebase-design-lqy`。
- 只处理有当前代码、调用链、测试或 diff 证据的问题；两个 skill 的原则不能替代这些证据。

## 流程

1. **锁定行为**
   - 检查目标文件、真实调用链、现有 diff 和项目约定，列出不得改变的行为与准备移除的问题。
   - 编辑前运行针对性回归测试；行为缺少保护时添加所需的最小测试。文档、skill 和配置使用相应 validator 或 smoke check。

2. **制定最小清理计划**
   - 聚焦死代码、同一知识的重复、无意义间接层、吞错、静默默认值、未经测试的替代路径和 Information Leakage。
   - 掩盖错误、绕过合同或缺少测试的回退应删除或改为显式失败。
   - 只有位于真实外部、版本兼容或故障安全接缝上，保留失败证据且主路径和回退路径都有测试的回退才可保留。

3. **逐类执行**
   - 每轮只处理一种问题，优先修复根因或共享路径；不要在旧路径旁叠加一条重复的“干净”路径。
   - 每轮结束后运行最相关的验证。新证据表明计划不成立时更新计划，范围或行为会改变时停止询问。

4. **验证并报告**
   - 运行项目已有的相关测试、lint、typecheck、构建、合同测试及静态或安全检查，并运行 `git diff --check`。
   - 确认 diff 最小、范围正确、没有调试残留；无法运行的检查必须说明原因和替代证据。
   - 简要报告范围、是否产生变更、完成的简化、行为证据、检查结果、回退或设计决策及剩余风险。
